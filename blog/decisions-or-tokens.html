Measuring Progress on ARC-AGI-3 When Every Run Scores Differently

Lessons from ARC Prize 2026 on building an agent for a world it has never seen, and on measuring whether a change really helped. Simple first, then deeper.

A headline, and a puzzle

In October, a small automated news site announced that I had joined the top ten of a global AI competition. A few weeks later I finished 26th. Both were true, and the gap between them is what this post is about.

To see why, start with something smaller. I wrote an agent that plays puzzle games. I ran it on 25 games, and it cleared 123 of the 183 levels.

Then I ran the exact same code again: same files, same settings, same kind of machine, same 25 games. It cleared 101.

That is a gap of 22 levels, with nothing changed. My best guess is the model's own randomness, but I could not prove it.

Everything else in this post follows from that gap. I will start simple and go a little deeper in each section. If you stop halfway, you still have the main idea.

In one line

When the same code can swing by 20 levels, a small improvement is invisible. Most of my ideas were small, so I could not tell which ones worked.

The games

ARC-AGI-3 is a set of small puzzle games on a grid. There are no instructions. The agent sees a picture, presses a key, sees what changed, and has to work out the rules by itself. Then it has to clear level after level. Every game is new to it.

The score rewards two things: how many levels you clear, and how few moves you use compared to a person. A human who needs 20 moves beats an agent that needs 60.

The competition, ARC Prize 2026, made it hard on purpose. The final run is offline, with one GPU, nine hours and 110 hidden games. At the end you get a single number back. No log, no replay. You never see what your agent did.

Where I started

I did not build this agent from scratch. I started from Daniel Franzen's public notebook, which runs Tufa Labs' open harness on a 4-bit Qwen model. Hundreds of teams started from that same notebook, so my job was to do better than a copy.

I worked with Claude, the AI from Anthropic, which wrote most of the code, the analysis and the first draft of this text. I set the goals and limits, checked the results, and made the final calls, including which two runs to hand in as my Final Submissions.

The question I asked was simple: what makes this agent score higher?

How a model acts in a world it has never seen

Think of the model as a scientist who has just been dropped into a strange lab. It reasons well, but it has never seen this equipment. What does it need? Not more brains. It needs a bench.

The harness is that bench. The public one I started from gives the model four things.

Eyes. Each game frame arrives as an enlarged picture, plus a diff that shows what just changed. The model's job is to spot cause and effect, so the effect is made easy to see.

A notebook. A Python session that stays alive between turns. The model can write its guess about the rules as code, run it on what it has already seen, and keep notes. "I think the blue square moves when I press right" becomes something it can check.

Hands. One action() call presses a key in the game. Only these moves count against the score. Thinking and notebook work are free. So the design pushes the model to think a lot, and to act only once it has a theory.

Undo. A wrong experiment should not cost the whole level.

That is the general recipe: see clearly, think on paper, test cheaply, act deliberately. It is not specific to puzzles. Any agent that has to learn a new environment on the fly needs some version of those four things. What I cannot tell you is how much each one is worth. That is the second half of this post.

Two ways to get better

Picture the agent as a student taking a very long exam. Two things decide how well they do.

First, how much they can write in the time allowed. For a model, the pieces of text it produces are called tokens. A faster server writes more tokens in nine hours. Second, how good each bit of thinking is. Do the tokens turn into clever moves, or into wandering?

So there are two ways to improve. Make the server faster, so there are more tokens. Or make each decision better, with smarter prompts, fixes or training. Every idea I tried falls into one of those two.

My paper asks exactly that, Decisions or Tokens? To answer it, I first had to learn how to measure. That part turned out to be the story.

A thermometer that jumps around

Imagine a thermometer that reads 20 degrees, then 14, in the same room, a minute apart. You turn on the heater. It now reads 17. Did the heater work? You cannot tell.

That was my situation. So before I tried any idea, I tried to measure the thermometer itself. I ran identical code twice, six times, on different days. In every pair, the second run was lower.

I checked boot times and start times. Day, order and machine all differ between the runs, and my data cannot separate them. On a single day, eight identical runs still ranged from 115 to 132.

My guess about the cause: the model picks its words with some randomness, and in a game one early choice can send a whole level a different way. That is a guess. The size of the swing is a measurement.

How many tries does it take to tell?

Think of a basketball player. You change their stance. They hit 6 of 10 shots before and 7 of 10 after. Did the stance help? You cannot say. You need many more shots.

Same here. The smallest gain you can reliably see shrinks only slowly as you add runs. It goes with the square root. Four times the runs buys you only half the blur.

With two runs per idea, I could only see gains above about 17 levels on one day, or 23 across days. Most of my ideas were worth less than 10.

To see a 10-level gain, I needed somewhere between 5 and 12 runs per idea, depending on which noise estimate holds. A run took about two hours and four dollars on a rented copy of the competition GPU. My budget allowed two or three per idea.

Something I wish I had known on day one

A test that cannot see an effect cannot say the effect is zero. "No difference" and "too small to see" are different sentences.

What I tried, and how each one ended

Over the next weeks I tried five kinds of ideas. Here is how each one ended, and what I can and cannot say about it.

A faster serverToo small to see

About 11% more tokens. By replaying logged attempts, that is worth roughly 4 levels. Real, but far under the noise.

Pausing the agent lessDid not hold up

Looked like +12.5 levels. When tested properly it was -2.5. The next section is about this one.

Four small harness fixesNoise-sized

Each led its control by -1 to +6 levels, +3.2 together. Noise alone explains that.

Fine-tuning on its own winsLooked worse, not proven

Three runs cleared 109, 115 and 117 levels. Two same-card controls cleared 132 and 130. I did not interleave them, so I make no causal claim.

Reinforcement learningPassed no gate

My small adapters never cleared the bar I set before running them.

Look at the pattern: almost none of these is a clear yes or a clear no. The ideas were not necessarily bad. My instrument was too blurry to judge them.

There is one more catch. My own rule for the four harness fixes, three runs against seven, would ship a change that truly loses 6 levels about one time in five. A cheap test can let a bad idea through, too.

The idea that fooled me

One idea looked wonderful. The agent thinks, then it has to act. When one burst of thinking runs long, the harness pauses it and starts a new request, which re-sends the whole start of the conversation. That wastes a lot of work.

So I moved the pause point from 2,048 tokens to 8,192. Runs with the change cleared 128 and 124 levels. Runs without it cleared about 111. That is +12.5. I shipped it.

Then I did the test I should have done first: both versions side by side on the same day, interleaved, six runs each. The answer was -2.5 levels, with a plausible range from -14 to +9.

The earlier gain was probably drift between days, differences between builds, and extra tokens. The change itself may still help a little; my data cannot exclude small gains. It only rules out the big one I thought I had.

A gain across different days is a hint, not a result.

Richard Feynman said the first rule is not to fool yourself, and that you are the easiest person to fool. This was that, in my own data.

Teaching the model from its own play

So far I had only changed the bench. The model itself can change too, and that is where fine-tuning comes in. It is the part I find most exciting, because it is where the agent can actually learn something.

My first attempt was simple. The agent played 127 practice games from an offline generator of games like the real ones. I kept every reply from a level it cleared and trained a small adapter on those (a rank-16 LoRA, one pass, about eight dollars on one rented GPU). It is like a student who only rereads the exam questions they already got right.

Training loss on held-out games fell 13.9%. The levels cleared fell too: 109 and 115 at full strength and 117 at half, against 132 and 130 for two plain runs on the same kind of card. I did not interleave them, so I do not call it proven. But it points one way.

My reading, which I have not tested: the filter kept almost everything. The agent clears most levels on those practice games, so "a cleared level" let in 63% of the training text, and half of it came from levels that took more than twice the human number of moves. I had trained the agent on its own slow habits. Lower loss on your own wins is not better decisions. A better filter would pick what the agent does not already do well, such as clearing a level in fewer moves.

Reinforcement learning taught me a different lesson. To stop training before the model drifts too far, I used a standard check, a KL estimate, with a stop at 0.02. Before the first update the adapter is zero, so the check was comparing the model with itself. It read 12.9.

The reason is that the training forward pass is not deterministic. The same tokens, run through the same model five times, agree exactly on only about 12% of tokens. So I clipped the estimate and read it net of that noise floor. If you use a KL guard, measure its floor first. In the end no adapter passed the gates I set before running them.

Neither approach beat the plain model. Both still taught me more than a win would have, because they showed where the real difficulty is: knowing what to teach the model, and knowing whether it worked.

The leaderboard shows your best draw

The competition lets you submit one scored run per day. The public leaderboard keeps your best one. So the number you see is not an average. It is a maximum.

Now back to the headline. On October 13, a 40.09 draw lifted me from 32nd to 9th on the public board, and a small automated news site, The Loose Goose, ran the headline "Vineeth joins the top ten." That was kind of them, and I am proud of it. But it was a one-day snapshot. By the deadline my best was 40.98 and I finished 26th of 5,073, in the top 0.5%.

Now look at the dots. My 17 valid draws averaged 34.6, and the spread is about 3.4. If you roll 17 times from a spread like that, the best one lands near 40 to 41, even if nothing you did worked. Try it.

What the teams ahead of me did

The top score on the final public board was 75.56, against my 40.98. What explains the gap? I do not know. The full write-ups open after the paper deadline, but the public forum posts say a few things.

First, speed. The first-place team reports about 3,800 tokens per second with all 110 games running at once. The sixth-place team reports going from about 600 to about 3,500. Mine was about 870 to 970.

The sixth-place team also reports its board score rising from 25.72 to 47.19 over two weeks in October, alongside large serving changes. That is a 20-point climb. I changed my speed by 11% and could not see the effect. They changed theirs several times over.

Second, training. The first-place team used the base model for roughly the first six hours, then switched to a model trained with reinforcement learning for the last three. The author says there is no clean test that isolates what the trained model added.

I measured the thermometer. I never found out how big the fire was.

Here is what I take from that. My results explain why a small speed-up was invisible. They do not say a big one is useless. The field made big moves and gained a lot. I measured small ones and could not tell. And the first-place team's author says there is no clean test for their training step either.

What I would do differently

If your work is tuning an agent, or anything where a run gives you one noisy number, here is what I would do.

First

Measure the noise first. Run identical code about eight times on one day, plus a few pairs across days. Do it before testing any idea.

Second

Know the smallest change you can see. With n runs per arm, it is about 2.8 times the noise, times the square root of 2 over n. If your idea is smaller than that, know it before you start.

Third

Interleave. Run the two versions side by side on one day. Gains measured across days are hints.

Fourth

Judge a small change by the behavior it targets. Write the pass rule first. Use the final score only to veto big harm.

Fifth

Write your stop rule before the first run. Otherwise every result will look like a reason to keep going.

None of this is special to games. A study of coding agents on SWE-Bench finds similar spread, so a single run per version could only detect about 6 points there.

And if you are building a general agent: give the model a way to see, a place to think on paper and a cheap way to test ideas, then measure every change with more care than feels necessary.

Limits, and thank you

This is one stack, one GPU, and 25 public games. I tuned and chose what to ship on those same games, so my development numbers may overstate how it does on new ones. Most of my results are null, and I say so. The scored private result is not in yet.
